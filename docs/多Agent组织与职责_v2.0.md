# RKA-3000 多 Agent 组织与职责 v2.0

- 文档版本：v2.0
- 日期：2026-03-19
- 适用仓库：`RKA-3000-desktop`
- 状态：建议版，待需求澄清后作为后续开发的组织基线

## 1. 调整背景

本版本用于替代“以文件夹拆分为主”的早期协作方式，改为更符合工业科学仪器软件项目的组织模型。

调整原因：

- 当前协作方式更偏执行导向，弱化了需求冻结和架构先行
- 业务控制逻辑、UI 编排逻辑、设备控制逻辑之间边界不够清晰
- 项目属于科学仪器控制软件，不应只按前后端/UI/数据库的常规软件角色来拆分

本版本目标：

- 先建立产品、架构、领域、实现、验证、交付的完整责任链
- 再在责任清晰的前提下做多 Agent 并行
- 避免继续出现“边开发边定义需求和结构”的情况

## 2. 组织原则

- 需求先冻结，开发再展开
- 架构先收敛，模块再并行
- 控制逻辑不放在 UI 层
- 设备通信、业务控制、数据持久化、算法分析、界面展示必须分层
- 任何 Sprint 启动前，必须有明确输入、输出、验收标准
- 主控 Agent 负责节奏与验收，但不替代架构职责

## 4. 每个 Agent 的明确边界

### Alex

  - Sprint 启动条件检查

  - 替代 `Iris` 做架构决策

  - 冻结目录结构演进路线

  - 大量业务代码落地
  - 文档交付和现场部署

### Leo

- 负责

  - 多设备抽象
  - 寄存器映射 profile
  - 诊断信息与错误分类
  - 模拟器与实机切换
- 不负责
  - 实验流程判断
  - 页面行为编排

### Emma

  - 调度 Leo 和 Ryan 暴露的接口

  - 直接定义寄存器地址

### Ryan

- 负责
  - 数据模型
  - 数据库迁移
  - 查询接口
  - 导出数据准备

### Mia

## 5. 推荐协作链路

```text
Alex
  ↓
Iris
  ├─ Leo
  ├─ Ryan
  ├─ Emma
  └─ Nina
        ↓
      Mia
        ↓
      Lily
        ↓
   Owen + Evan
```

说明：

- `Alex + Iris` 决定做什么、怎么分层、先后顺序
- `Leo / Ryan / Emma / Nina` 负责核心能力基线
- `Mia` 在核心接口稳定后接 UI
- `Lily` 从接口冻结后开始扩大测试覆盖
- `Owen + Evan` 在功能收敛后完成交付闭环

## 6. 当前项目推荐分层

建议后续逐步收敛为以下结构：

```text
src/rka_desktop/
├── controllers/        # UI 与业务服务之间的控制编排层
├── services/           # 业务服务、执行引擎、分析服务
├── models/             # 数据实体、状态定义
├── db/                 # 数据库、迁移、查询仓储
├── hardware/           # 设备抽象、多设备驱动、诊断
├── ui/                 # 页面、组件、对话框
├── core/               # 配置、日志、基础设施
└── utils/              # 纯工具与通用函数
```

特别说明：

- 当前项目里部分控制编排还在 `ui/main_window.py`
- 这不应继续扩大
- 后续应由 `Iris + Emma + Mia` 联合把控制流逐步迁到 `controllers/`

## 7. 建议的开发阶段

  - 功能边界表
  - 系统分层图

### 阶段 B：核心接口冻结

- 负责人：`Leo + Ryan + Emma`
- 输出：
  - 设备接口

  - 数据查询与持久化接口

### 阶段 C：领域算法与 UI 接入

- 负责人：`Nina + Mia`
- 输出：

  - 历史分析能力
  - UI 页面集成

### 阶段 D：验证与交付

- 负责人：`Lily + Owen + Evan`
- 输出：
  - 联调测试矩阵
  - 用户手册
  - 打包与发布材料

## 8. 当前版本下的优先事项

在需求没有再次澄清前，建议暂停继续铺功能面，先做以下事项：

1. 重新确认产品范围
2. 重新确认“控制层”是否独立建目录
3. 重新确认历史数据、报告和算法分析是不是 MVP 范围
4. 重新确认设备侧最终联调目标，是“单控制器 MVP”还是“多设备正式联调”

## 9. 对现有分工的修正结论

原分工不是不可用，但存在以下结构性问题：

- 缺产品角色
- 缺架构角色
- 缺算法角色
- 缺构建发布角色
- `Emma` 的职责过窄，应扩展到控制层与业务服务层
- `Mia` 的 UI 角色需要更严格地与业务逻辑隔离
- `Alex` 不应同时承担 PM、架构师、实现者三种角色

因此，后续建议以本版职责定义为准，不再只使用旧版“通信 / 执行引擎 / UI / 数据 / 测试 / 文档”六分法。
